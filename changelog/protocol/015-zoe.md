# Zoe

## Summary

Zoe introduces ZK proof version `%3` at height `120400`. Version `%3`
preserves the version `%2` AIR and proof layout, but binds the extra composition
polynomial to committed trace work at the post-commitment DEEP challenge and
domain-separates the mining digest from Fiat-Shamir output. It also binds the
new proof-version tag into post-activation block IDs and closes the height-zero
proof-version/checkpoint bypass.

## Motivation

In versions `%0` through `%2`, proof object `5` is the extra composition
polynomial `P`, and proof object `6` contains trace evaluations at a challenge
sampled after `P`. Both objects are in the seven-object PoW prefix, while the
mega-extension commitment is object `7`.

That order leaves an affine grinding degree of freedom. A miner can change one
coefficient of `P`, derive the resulting challenge, and repair a suitable
coordinate in object `6` so the verifier's first equality still holds. The
expensive trace computation can be reused while producing additional PoW
candidates.

Moving an additional late trace-codeword Merkle root into the PoW prefix is not
an adequate repair. A miner can change one received-word leaf and update its
logarithmic Merkle path to obtain many cheap roots. With only a small number of
random openings, most attempts do not query the changed leaf. Reed-Solomon
minimum distance applies between valid codewords; it does not make a root
commitment to a nearby invalid received word expensive to vary.

## Technical Specification

### Proof version

The proof-version union gains `%3`. Version `%3` uses the same tables,
constraints, and serialized proof-object sequence as `%2`.

Consensus selects proof versions by block height:

```text
height < 6750             -> %0
6750 <= height < 12000    -> %1
12000 <= height < 120400  -> %2
height >= 120400          -> %3
```

This is a forward-only verifier change. A block is always checked against the
proof version selected by its own height, so a current node continues to apply
the historical `%0`, `%1`, and `%2` rules to already-mined blocks.

The height-selected proof-version predicate is shared by normal and genesis
validation. Height zero therefore requires `%0`; it cannot be retagged to a
later proof version even though historical block IDs do not bind the tag.

### Post-commitment extra-composition check

Let `P(X)` be proof object `5`. The existing verifier samples the DEEP point
`y` after absorbing the mega-extension and composition commitments (objects `7`
and `8`) and reads committed trace evaluations in object `9`.

For `%3`, the verifier additionally requires:

```text
C_extra(object9, y) = P(y)
```

The later DEEP quotient, FRI, and Merkle-opening checks bind object `9` to the
trace commitments. No new proof object is added, and an honest prover performs
no additional commitment or Merkle work.

For `%3`, object `5` must also be a structurally valid canonical polynomial
(`P = bpcan(P)`) with at most `D` coefficients, where the processed extra-
constraint degree bound is `D - 1`. Canonical form removes trailing-zero
encodings as transcript entropy; the upper bound prevents an out-of-range term
from bypassing the advertised degree. The bound is not an exact-length rule,
because an honest random linear combination can have a lower degree through
leading-coefficient cancellation. Consensus has separately required canonical
PoW polynomials since height `112500`; the `%3` verifier makes both invariants
explicit at the proof boundary as well.

Every `%3` polynomial/vector payload must have a logical length matching its
backing atom. Merkle openings additionally have exact semantic widths: base,
extension, and mega-extension leaves match their respective trace widths;
composition leaves match the statically derived number of composition pieces;
and each FRI opening contains exactly one folding coset. The composition-root
piece count must equal the maximum constraint degree. These checks prevent a
miner from changing a hashed length header or appending verifier-ignored values
to obtain a new root or Fiat-Shamir challenge while presenting the same
codeword values. Native decoding rejects a claimed polynomial length before any
unsafe slice is formed unless the backing atom has the historical word shape;
for legacy versions this means it contains at least the declared payload words,
including historically ignored suffixes. The `%3` raw-proof boundary
additionally requires the exact size and terminal marker.
That version gate leaves historical `%0` through `%2` marker acceptance
unchanged while making Hoon and native `%3` decoding agree.

### Per-table trace degree binding

The DEEP polynomial also contains an independently weighted batch

```text
R(X) = sum rho[t,j] * X^(H - h[t]) * T[t,j](X)
```

where `H` is the maximum table height, `h[t]` is table `t`'s declared height,
and `T[t,j]` ranges over every committed base, extension, and mega-extension
trace column. The cubic-extension weights `rho[t,j]` are sampled after the
trace roots and claimed DEEP evaluations are fixed.

An honest column has degree strictly less than `h[t]`, so every term in `R`
has degree strictly less than `H`. Adding a multiple of the table zerofier
`X^h - 1` preserves every row value but creates a degree-`H` term in `R`, which
the existing strict FRI bound rejects except with the probability of a random
leading-coefficient cancellation.

### Mining-domain separation

All versions continue to mine over proof objects `0` through `6`, which already
include the base and extension trace roots at objects `2` and `3`. No additional
late root, especially the mega-extension or composition root at objects `7`
and `8`, is moved into the PoW prefix. For `%0` through `%2`, the PoW digest is
unchanged. For `%3`, let `prefix_digest` be the legacy Tip5 digest of objects
`0` through `6`; the mining digest is:

```text
Tip5([leaf+%zkpow-v3 hash+prefix_digest])
```

This prevents the mining digest from being reused as an unlabeled
Fiat-Shamir squeeze while retaining the inexpensive, pre-Merkle mining loop.

### Block identity

The historical full-proof digest hashes proof objects but not the proof-version
tag or proof-stream bookkeeping fields. Version `%3` blocks instead commit a
tagged digest of all verifier-visible proof fields in the block ID. Its domain
tag is:

```text
Tip5([
  leaf+%zkblk-v3,
  leaf+%3,
  hash+legacy_full_proof_digest,
  list+(hashes),
  leaf+read_index
])
```

Versions `%0` through `%2` retain their exact historical block-proof digest.
This prevents a `%3` block from being retagged as `%2`, or having its proof
cache/index metadata mutated, under the same block ID. It changes no
already-mined block ID or proof Fiat-Shamir state.

### Genesis checkpoint

When the configured genesis seal identifies realnet, genesis intake requires
the height-zero digest in the checkpoint map. Custom networks retain their
existing behavior and skip realnet checkpoints. This preserves the canonical
already-mined genesis while rejecting alternate legacy proof encodings or
proof-version retags under the realnet seal.

## Activation

- **Height**: `120400`
- **Target date**: approximately `2026-08-08`
- **Basis**: [NockBlocks](https://nockblocks.com/) reported height `116492` and
  target block time `150` seconds on `2026-08-01`. The cutover is `3908` blocks
  later, approximately 6 days 18 hours 50 minutes at target cadence.
- **Coordination**: This is an emergency security cutover. Miners and validating
  nodes must deploy before the activation height.

## Migration

### Requirements

- Software version: the Zoe reference implementation or newer.

### Configuration

None.

### Data Migration

None. Historical blocks and proofs are not rewritten. During load, every node
with a recognized network identity audits the canonical tip and (once crossed)
the stored height-`120400` activation page; realnet additionally audits every
pinned checkpoint page. The audit checks the height-selected proof version,
page digest, canonical proof-stream envelope, and expected checkpoint ID where
one is pinned. Durable kernel state advances from `%10` to `%11`; that one-time
migration audits every stored page at or above the boundary, including the full
canonical suffix and noncanonical forks. This catches both a stale `%2` fork
that could later become canonical and a mixed canonical suffix produced by an
intermediate check-disabled custom-network build. On subsequent `%11` loads,
only noncanonical post-boundary entries are decoded and audited before the same
load pipeline removes orphaned entries. Canonical pages are identified from the
height index without cueing their proofs, so recurring restart cost does not
grow with the post-Zoe chain; the boundary page and current tip are still
checked explicitly.
This rejects a pre-Zoe node state that has already accepted `%2` at the `%3`
boundary, including on custom networks. A pending page also repeats the cheap
version gate when its final transaction arrives, so persisting it across the
upgrade cannot bypass activation.

The load audit is a migration consistency check for state produced by the
node itself, not full proof replay. Operators must fully revalidate any
untrusted or externally edited state import.

A born node with no accepted chain is left untouched while it waits for
genesis, but only when its chain-bearing stores are empty. Ambiguous or partial
chain state is reset rather than preserved in a permanently wedged state. A
reset retains the BTC anchor, genesis seal, initialization state, and mining
configuration so genesis intake can safely resume.

### Steps

1. Deploy the upgraded verifier and miner before height `120400`.
2. Confirm candidate blocks below the boundary still request `%2` proofs.
3. Confirm candidate blocks at and above the boundary request `%3` proofs.

### Rollback

Do not roll back to a `%2`-only node after activation; it will diverge from the
network's proof-version rule.

## Backward Compatibility

The proof noun gains a new discriminant, so software predating Zoe cannot
decode or validate post-activation `%3` blocks. Upgraded software remains fully
compatible with historical blocks because the stronger equation and mining
domain apply only to `%3` proofs.

## Security Considerations

The second equality is evaluated at a cubic-extension-field challenge sampled
after both relevant roots are committed. For any fixed inconsistent `P`, the
difference from the trace-derived extra composition is a nonzero polynomial;
the probability that it vanishes at `y` is bounded by its degree divided by the
extension-field size.

That identity argument requires the committed trace to be in each table's
claimed Reed-Solomon degree class. The normalized trace batch enforces those
per-table degree bounds. In particular, a miner cannot add `c(X^h - 1)` to a
trace column: although that mutation is invisible on the `h` table rows and its
ordinary DEEP quotient fits the old global bound, its normalized term has
degree `H` and fails v3 FRI.

The late roots are intentionally not added to PoW. Cheap mutations of a
committed received word can vary a Merkle root, but each such root only samples
another `y`; it does not let the miner choose `P` after seeing `y`.

The base and extension roots were already part of the historical PoW prefix.
Zoe removes representation-only root nonces: a changed length header or ignored
leaf suffix is rejected even if its leaf is queried. It does not eliminate the
distinct, pre-existing sparse-Merkle strategy of changing an actual
received-word value and hoping the random openings miss that position. That
strategy is part of the proximity-error term below and is the remaining
Merkle-twiddling skip point, rather than a deterministic always-valid nonce.

Soundness is nevertheless bounded by both the cubic-extension identities and
the configured DEEP/FRI sampling. With expansion factor `64` and eight spot
checks, the direct proximity term is approximately `(1/64)^8 = 2^-48` per fixed
transcript. A conservative per-transcript summary is:

```text
epsilon <= deg(P - C_extra)/p^3 + 1/p^3 + epsilon_FRI
```

Grinding `Q` distinct post-PoW transcript suffixes scales this bound by at most
approximately `Q`. Zoe removes the cheap deterministic repair; it does not
raise the protocol above its existing roughly 48-to-50-bit FRI security floor.

## Operational Impact

Honest proof size and Merkle work are unchanged. Verification adds one
extra-composition evaluation at the existing DEEP point plus one evaluation of
`P`. The `%3` mining digest adds one fixed tagged Tip5 hash after the legacy
seven-object prefix digest.

## Testing and Validation

- `%0`, `%1`, and `%2` public proof fixtures continue to verify unchanged.
- A genuine `%3` proof generated under the normalized DEEP rule verifies in
  both the Hoon and native Rust verifiers.
- A `%2` transcript merely relabeled as `%3` is rejected because its DEEP
  commitment does not include the v3 degree-binding batch.
- `%3` encodes and decodes as the noun atom `3`.
- Height `120399` selects `%2`; heights `120400` and `120401` select `%3`.
- Height zero selects `%0`, and an identical-object `%0` proof retagged `%1`
  is rejected even though the legacy block digest does not bind that tag.
- Realnet accepts the pinned height-zero digest and rejects an alternate;
  fakenet genesis seals continue to bypass the realnet checkpoint map.
- The stored-page load audit accepts a height-zero `%0` page and rejects its
  identical-object `%1` retag, nonempty hash cache, or nonzero read index.
- Load rejects missing pinned checkpoint pages, a preloaded `%2` activation
  page on realnet or a custom network, a stored post-cutover `%2` side fork,
  a mixed `%3/%2/%3` canonical suffix during the one-time state-`%11`
  migration, and ambiguous partial-genesis state; it preserves a genuinely
  empty born state that is waiting for genesis.
- A pending height-`120400` `%2` page is rejected when transaction-complete
  validation resumes after the upgrade.
- Genesis intake cleanly rejects a wrong proof version, a missing production
  proof, and the wrong page variant; test-only PoW skipping does not skip the
  version gate when a proof is present.
- `%2` PoW remains the legacy prefix digest; `%3` PoW differs by its explicit
  domain hash.
- `%2` and `%3` proofs with identical objects retain the same raw transcript
  digest but produce different block-proof digests and block IDs.
- Retagging a `%3` block as `%2` while retaining its digest fails the page
  digest check.
- A table-zerofier shift reaches degree `H` in the normalized trace batch and
  is rejected by the strict `< H` FRI bound.
- `%3` rejects a trailing-zero encoding of object `5` and a canonical object
  `5` whose degree exceeds the processed extra-constraint bound.
- `%3` rejects malformed array length headers, oversized trace/composition
  openings, a wrong composition-piece count, and non-coset-sized FRI openings;
  the Hoon and native decoders/verifiers agree on these shapes.
- Proof-stream push/pull preserves `%3` through the FRI sub-verifier. A
  noncanonical terminal marker remains decodable under the historical `%2`
  rule but is rejected at both Hoon and native `%3` proof boundaries.
- `%3` rejects non-based Merkle sibling limbs before any release hash jet can
  normalize them modulo the field.
- Adversarial review must test coefficient/evaluation repair, sparse Merkle-root
  grinding, transcript challenge bias, and downgrade/activation behavior.
